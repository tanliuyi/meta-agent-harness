# Lovart 参考产品规范：AI Design Agent Workbench

状态：Draft / Reference
适用范围：`packages/desktop`、设计相关 Pi Extension、图像/网页能力与 Desktop Workbench

> 本文是基于 Lovart 公开产品页面和公开评测形成的参考产品设计，不是 Lovart 的官方规格，也不要求实现与 Lovart 兼容。Lovart 的 MCoT、模型编排、资产数量和质量指标属于其公开宣传；本项目应以可观察行为、实验数据和自身约束为准。

## 1. 摘要

本产品不是在通用聊天 Agent 旁边增加一个生图按钮，而是把设计工作建模为一个可持续的项目：

```text
设计 brief
  -> 设计计划
  -> 资产清单
  -> 多模型生成
  -> 画布评审
  -> 局部修改
  -> 品牌校验
  -> 多格式交付
```

目标是让用户从“写 Prompt 并反复重生成”转变为“描述目标、选择方向、修改局部、验收资产包”。

核心判断：

```text
设计体验 = 模型能力
          × 设计领域约束
          × 项目级上下文
          × 可控编辑
          × 视觉反馈速度
          × 交付完整度
```

Lovart 参考的重点在后五项，而不只是更换一个图像模型。

## 2. 产品定位

### 2.1 一句话定位

面向设计师、营销人员和小型团队的项目型 AI 设计工作台：从一份 brief 生成、评审、修改并交付一组保持视觉一致的设计资产。

### 2.2 与通用 Agent 的边界

通用 Agent 的工作单位通常是一次问题和一次工具调用；Design Agent 的工作单位是一个设计项目和它的资产图谱。

| 维度 | 通用 Agent | Design Agent |
| --- | --- | --- |
| 输入 | 自然语言问题 | brief、受众、渠道、品牌资产、参考图 |
| 状态 | 对话与文件 | 项目、品牌规范、决策、变体、资产谱系 |
| 规划 | 临时决定工具调用 | 先生成设计策略和资产计划 |
| 结果 | 文本、单张图片或文件路径 | 可评审的多资产设计包 |
| 修改 | 重新描述并重新生成 | 点选区域，只修改目标元素 |
| 交付 | 用户自行整理文件 | 按渠道导出并保留版本关系 |

### 2.3 目标用户

- 设计师：减少重复排版、尺寸适配、背景清理和变体生产，把时间留给方向与审美判断。
- 营销人员：从活动 brief 快速得到社媒、广告、邮件和落地页素材。
- 企业主和创作者：没有完整设计团队，但需要统一、可发布的品牌素材。
- 小型团队：需要在同一个视觉空间中评审、决策和交接，而不是在聊天附件中找版本。

## 3. 产品目标

### P0 目标

1. 用户可以创建一个持久的设计项目。
2. 用户可以上传参考图和品牌资产，或直接输入文字 brief。
3. Agent 可以把模糊需求转换为结构化设计计划。
4. 一个计划可以生成多个渠道和尺寸的资产。
5. 所有变体、参考图、决策和资产状态在一个视觉工作区中可见。
6. 用户可以针对单个资产提出修改，而不影响其他资产。
7. 用户可以继续上次项目，不需要重新描述品牌和已确认方向。

### P1 目标

1. Brand Kit 自动约束颜色、字体、Logo 和视觉风格。
2. 支持区域级编辑、对象替换、颜色修改和文字修改。
3. 支持资产谱系：从哪个资产、哪个操作、哪个模型生成了当前版本。
4. 支持自主执行和协作执行两种模式。
5. 支持 PNG、JPEG、SVG、PDF 等适合当前资产类型的导出。
6. 支持生成完成后的文字、尺寸、品牌和格式检查。

### P2 目标

1. 支持视频、音频、3D 等更多媒体类型。
2. 支持团队评论、审批和角色权限。
3. 支持可复用的 Design Skill，例如“电商主图”“发布会海报”“品牌社媒包”。
4. 支持跨项目复用 Brand Kit、Skill 和已确认的设计决策。

## 4. 非目标

首期不实现：

- 替代 Figma、Illustrator、Photoshop 的完整像素级编辑能力；
- 法律意义上的商标可注册性、版权清理或品牌策略咨询；
- 完整的视频剪辑、时间线和动画关键帧系统；
- 允许 Agent 在未展示计划的情况下无限生成大量资产；
- 把 Lovart 的内部模型、提示词、MCoT 实现或品牌文案复制到本项目；
- 把隐藏模型推理过程持久化或展示为“思考全文”；只保存结构化计划、约束和简短决策摘要。

## 5. 产品原则

### 5.1 先理解项目，再生成像素

Agent 应先确认受众、目标、渠道、必须保留的内容和交付规格，再调用生成模型。用户只要求一张图时可以跳过完整计划，但多资产任务必须形成计划。

### 5.2 视觉结果是第一等公民

聊天用于表达意图和修改要求，画布用于比较、选择、定位和确认结果。结果不能只以 Markdown 图片或文件路径出现在消息末尾。

### 5.3 保留已正确的部分

修改的默认语义是局部修改。用户要求“只改标题颜色”时，系统应把标题作为目标区域，把产品、构图、背景和光线列为保护约束。

### 5.4 约束应持久化

颜色、字体、Logo、尺寸和禁用项不应依赖用户每轮重复输入。约束有版本，资产记录使用生成时的 Brand Kit 版本。

### 5.5 默认协作，明确授权自主执行

默认先展示设计计划和少量首轮方案。用户可以批准计划后批量生成，也可以打开自主模式，让 Agent 生成完整方案后再统一评审。

### 5.6 每个结果都可解释、可回退

用户应能看到资产来自哪个 brief、参考图、模型和操作，并能回到父版本。解释是结构化摘要，不是暴露隐藏链式推理。

## 6. 产品信息架构

```text
Design Projects
├─ Project list
├─ New project
└─ Project Workbench
   ├─ Brief / plan panel
   ├─ Chat and agent activity
   ├─ Infinite or bounded canvas
   ├─ Asset variants and comparison
   ├─ Brand Kit / constraints inspector
   ├─ Artifact detail and lineage
   └─ Export / handoff panel
```

### 6.1 Project list

列表项显示：

- 项目名称和最近更新时间；
- 当前阶段：草稿、规划、生成、评审、已交付或失败；
- 资产数量和待处理项；
- 使用的 Brand Kit；
- 最近一次错误或需要用户决策的状态。

### 6.2 Project Workbench

建议采用三部分布局：

```text
左侧：brief、计划、品牌和项目导航
中间：画布、参考图、资产变体和比较
右侧：选中资产的属性、局部编辑、谱系和导出
底部或侧边：聊天、任务进度和待确认操作
```

布局可以响应式变化，但画布和选中资产不能因为工具调用状态变化而跳动。工具按钮使用图标和 tooltip；显式命令使用图标加短文本。

## 7. 核心用户流程

### 7.1 创建项目

1. 用户输入项目目标，例如“为夏季户外水杯做一组社媒 campaign”。
2. 用户可补充受众、渠道、尺寸、必须出现的文案和参考图。
3. 用户可选择已有 Brand Kit 或上传 Logo、颜色、字体和示例素材。
4. Agent 提取缺失信息；缺少的信息必须以有限问题询问，不要无限追问。
5. 系统创建项目并保存原始 brief、输入素材和初始约束。

### 7.2 生成设计计划

计划至少包含：

- 目标受众和设计目标；
- 视觉方向和不应偏离的参考；
- 资产清单；
- 每个资产的渠道、尺寸和格式；
- 共用视觉规范；
- 每个资产的必须保留内容；
- 预计使用的模型能力；
- 交付前检查项。

协作模式下，用户必须可以编辑或批准计划。自主模式下，系统可以自动批准低风险计划，但仍应保留计划记录。

### 7.3 生成资产

1. 系统按照资产依赖关系调度任务。
2. 独立资产可以并行生成。
3. 共享视觉规范和 Brand Kit 版本进入每个任务。
4. 每个任务产生一个或多个带谱系的 Artifact。
5. 生成中展示阶段和资产级状态，不只显示一个总进度条。
6. 单个资产失败不应丢弃同一计划中已经成功的资产。

### 7.4 评审和局部修改

用户可以：

- 选择一个变体作为当前方向；
- 并排比较变体；
- 点击区域并输入修改要求；
- 修改标题、颜色、对象、背景或构图；
- 拒绝某个方案并记录原因；
- 从当前版本创建新分支；
- 将一条意见应用到一组同类资产。

### 7.5 导出和交付

导出前显示：

- 资产数量和缺失项；
- 渠道和尺寸；
- Brand Kit 检查结果；
- 文字可读性和溢出检查；
- 文件格式和色彩空间；
- 使用的模型和生成时间；
- 商用权利提示，以实际供应商条款为准。

导出结果应是有目录结构和 manifest 的项目包，而不是一堆无关系的文件。

### 7.6 恢复项目

恢复项目时，系统应加载：

- 最近一次有效计划；
- Brand Kit 版本；
- 当前资产和父版本；
- 已接受、已拒绝和待处理的决策；
- 未完成任务及可重试原因。

不应把所有历史聊天全文重新塞入模型上下文，而应使用项目摘要和相关资产上下文。

## 8. 功能需求

### 8.1 Brief 与计划

| 编号 | 需求 | 验收行为 |
| --- | --- | --- |
| PRD-DESIGN-001 | 创建设计项目 | 用户输入 brief 后得到可恢复的项目记录 |
| PRD-DESIGN-002 | 结构化 brief | 受众、目标、渠道、尺寸、文案约束可单独编辑 |
| PRD-DESIGN-003 | 设计计划 | 多资产任务先生成资产清单和共享视觉规范 |
| PRD-DESIGN-004 | 计划审批 | 用户可以批准、修改、拒绝或要求重新规划 |
| PRD-DESIGN-005 | 有限澄清 | 缺少关键字段时一次展示最小问题集合 |

### 8.2 参考素材和 Brand Kit

| 编号 | 需求 | 验收行为 |
| --- | --- | --- |
| PRD-DESIGN-010 | 参考图 | 参考图有用途标签，例如产品、构图、风格或颜色 |
| PRD-DESIGN-011 | Brand Kit | Logo、颜色、字体和语气可保存为版本化资产 |
| PRD-DESIGN-012 | 品牌约束 | 后续生成自动带入选定 Brand Kit 版本 |
| PRD-DESIGN-013 | 必须保留项 | 用户可标记产品形态、文案、Logo 等不可改变内容 |
| PRD-DESIGN-014 | 约束解释 | 违反约束时系统提示原因和可选替代方案 |

### 8.3 画布和变体

| 编号 | 需求 | 验收行为 |
| --- | --- | --- |
| PRD-DESIGN-020 | 资产卡片 | 每个结果显示类型、尺寸、状态、父版本和操作 |
| PRD-DESIGN-021 | 变体比较 | 多个变体可并排查看、选择和归档 |
| PRD-DESIGN-022 | 版本谱系 | 从资产可以回到父版本和生成操作 |
| PRD-DESIGN-023 | 画布历史 | brief、决策和资产在同一项目空间中可恢复 |
| PRD-DESIGN-024 | 视觉状态 | 生成中、成功、失败、待审核和已接受状态清晰区分 |

### 8.4 局部编辑

| 编号 | 需求 | 验收行为 |
| --- | --- | --- |
| PRD-DESIGN-030 | 选区编辑 | 用户点击或框选区域后发起修改 |
| PRD-DESIGN-031 | 保护区域 | 未选区域作为保持约束传入编辑任务 |
| PRD-DESIGN-032 | 文字修改 | 修改海报文字时不默认重做整个画面 |
| PRD-DESIGN-033 | 对象修改 | 支持删除、替换、改色和背景清理 |
| PRD-DESIGN-034 | 编辑回退 | 每次局部编辑产生新版本，不覆盖父版本 |

### 8.5 交付和检查

| 编号 | 需求 | 验收行为 |
| --- | --- | --- |
| PRD-DESIGN-040 | 多格式导出 | 根据资产类型提供适合的格式选项 |
| PRD-DESIGN-041 | 渠道尺寸 | 资产计划中的尺寸全部可检查和批量导出 |
| PRD-DESIGN-042 | 品牌检查 | 导出前报告颜色、字体、Logo 和文案问题 |
| PRD-DESIGN-043 | 项目包 | 导出文件包含资产 manifest 和版本关系 |
| PRD-DESIGN-044 | 部分成功 | 一个资产失败时其他资产仍可交付 |

## 9. 工作模式

### 9.1 Guided collaboration

默认模式。Agent 执行顺序为：

```text
brief -> plan -> user approval -> first variants -> user direction -> refinement -> export
```

适用于品牌探索、客户评审和需要保留创意方向的项目。

### 9.2 Full autonomous

用户明确授权后，Agent 可以：

- 自动补全低风险设计计划；
- 批量生成资产；
- 对明显失败的结果自动重试有限次数；
- 在完成后统一展示方案和检查结果。

以下操作仍需要用户确认：

- 覆盖现有 Brand Kit；
- 删除或替换用户明确标记的产品/Logo；
- 导出或发布到外部服务；
- 使用高成本模型的大批量任务；
- 任何不可逆文件操作。

## 10. 产品状态

项目状态：

```text
draft -> planning -> awaiting-approval -> generating
      -> reviewing -> exporting -> completed
      -> partially-failed | failed | cancelled
```

资产状态：

```text
planned -> queued -> generating -> ready -> selected -> exported
                           \-> failed -> retrying
ready ----------------------\-> rejected | archived
```

状态必须支持取消、重试和旧版本查看。失败状态包括稳定错误类别和用户可执行的下一步。

## 11. 质量指标

首期不直接采用 Lovart 的宣传数字，先建立同一 brief 的基线，再追踪以下指标：

- 首个可用方案耗时；
- 首轮方案被用户选中的比例；
- 每个资产平均重试和重提示次数；
- 局部编辑后未选区域的保持率；
- Brand Kit 约束通过率；
- 多尺寸资产的完成率；
- 从 brief 到完整交付包的成功率；
- 用户恢复项目后重新解释背景的次数；
- 单次生成的模型成本、延迟和失败率；
- 用户在画布上完成评审所需的操作数。

建议的对比基线：当前 `image_generate` 工具流程、仅聊天的通用 Agent 流程，以及 Design Workbench 流程。

## 12. 标准评测任务

固定同一份 brief、参考图和 Brand Kit，至少评测：

1. 一个新品 campaign，生成主视觉、社媒横版、社媒竖版和邮件头图。
2. 只修改海报标题颜色，验证产品、构图和背景保持不变。
3. 第二天恢复项目，验证品牌和已确认方向仍然存在。
4. 新增一个渠道尺寸，验证是否复用已有视觉规范。
5. 一个资产生成失败，验证其他资产仍然可以预览和导出。
6. 导出完整项目包，验证 manifest、版本关系和尺寸信息。

评测结果必须同时记录客观指标和设计师主观评分，不能只用图片相似度判断质量。

## 13. 分阶段路线

### Phase 0：设计工作流验证

- 一个 Design Project；
- brief 和参考图；
- 结构化 Design Plan；
- 4 个固定资产类型；
- 变体卡片和基础比较；
- Guided 模式；
- 从现有 `pi.image-gen` 生成并保存资产。

退出条件：用户可以完成一次从 brief 到多资产预览的完整流程。

### Phase 1：交付闭环

- Brand Kit；
- 资产谱系；
- 画布历史；
- 局部编辑；
- 多格式导出；
- 导出前检查；
- 失败任务的独立重试。

退出条件：用户可以在不重新生成全部资产的情况下完成一轮真实修改并导出。

### Phase 2：Agent 编排

- 模型能力路由；
- 资产依赖图和并行调度；
- Autonomous 模式；
- 研究、竞品和参考素材阶段；
- 结构化质量评估。

退出条件：多资产任务不再依赖用户手动逐个描述和整理。

### Phase 3：团队和更多媒体

- 评论和审批；
- 可复用 Design Skill；
- 视频、音频和 3D；
- 项目级权限与审计。

## 14. 风险与取舍

- Lovart 的公开页面主要是自述，不能把宣传文案当成性能承诺。
- 过早实现无限画布、PSD 或完整图层编辑会显著扩大范围；首期应先验证一个 campaign 工作流。
- Brand Kit 只能提高一致性，不能替代人工品牌判断和商标审核。
- 多模型路由会增加成本、延迟和错误组合；没有能力 metadata 时不应按模型名称硬编码。
- 自主模式可能放大错误和费用，必须有预算、资产数和用户确认边界。
- 局部编辑依赖模型和编辑 API 的能力，不能仅靠 Prompt 宣称“保持其他区域不变”。
